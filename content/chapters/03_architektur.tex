\section{Architektur}

\subsection{Anforderungen für Architektur}

Die Referenzarchitektur wird aus fachlichen, organisatorischen, technischen und sicherheitsbezogenen Anforderungen abgeleitet. Diese werden auf Basis von fachlichen Interviews, technischen Randbedingungen und der Literatur gebildet. 

Daher ist der Ausgangspunkt nicht die Frage, was für Technologien verfügbar sind sondern welchen Anwendungsfall das System erfüllen soll und unter welchen Randbedingungen es betrieben wird. Hier sind sowohl Unternehmerischen Richtlinien wie auch Technische Begebenheiten zu berücksichtigen, sodass sich das Multi-Agenten-System nahtlos klassische Cloud Infrastrukturen einbinden lassen.

Durch die Analytische Betrachtung durch geeignete Threat-Modeling Prozesse werden weitere Designentscheidungen getroffen, welche fortlaufende Architekturentscheidungen begründen sollen.

Dies könnten zum Beispiel zusätzliche Kontrollmechanismen, Protokollentscheidungen oder auch stärkere zentralisierung/verteiltes Design des Multi-Agenten-Systems sein.




\subsection{Bisherige Überlegungen zur Architektur}

Die bisherige Zielarchitektur orientiert sich an einem modularen Multi-Agenten-Ansatz mit getrennten Verantwortlichkeiten. Ein Zentraler Orchestrator und/oder Workflow Controller erscheint für Multi-Agenten-Systeme eine plausible Kernkomponente. \cite{georgeff_communication_1983,jennings_roadmap_1998, vashishtha_cosmic_2026}

Dieser nimmt Anfragen entgegen, strukturiert Aufgaben, delegiert Teilaufgaben an spezialisierte Agenten und konsolidiert Ergebnisse. \cite{sycara_distributed_1996, xue_all--one_2024} Diese Verarbeitungskette wird durch eine Kombination aus deterministischen und LLM-Basierten Entscheidungen realisiert. Damit werden Koordination, Kontrolllogik und Fehlerbehandlung in dieser Instanz gebündelt, in welcher der Gesamtprozess transparent strukturiert werden kann. \cite{wong_adding_2000} 

Insgesamt erhöhen deterministische Abläufe die Kontrollierbarkeit des Systems, jedoch auf Kosten der Flexibilität in Hinblick auf Erweiterung mit zusätzlichen Agenten. Diese müssen nämlich in Deterministische Abläufe mit eingebunden werden. 

Der im Anhang beschriebene Anwendungsfall \ref{Anwendungfälle} beschreibt ein MAS das Nutzer*innen bei unterschiedlichen Komplexen Wissensaufgaben assistiert. Dem Orchestrator stehen für diese Aufgabenbewältigung aktuell 3 Spezialisierte Agenten zur Verfügung. 

Ein 'Websearch' Agent, welcher als Input einen String erhält, diesen Aufbereitet und eine oder mehrere Websuchen über die Google API durchführt. Die Ergebnisse werden neu aggregiert und nach einem durch das LLM vergebenen 'relevance score' sortiert. Anschließend werden die Suchergebnisse zurückgegeben.

Zusätzlich steht ein 'Planner' Agent zur Verfügung. Dieser benötigt wiederum ein String als Input, welcher durch ein LLM aufbereitet wird indem der Plan konkretisiert wird und durch Zielkriterien \footnote{Dies umfasst: Umfang der Ausarbeitung, Erwartete Struktur des Ergebnisses, Schwerpunkt: Theorie, Machbarkeit, Praxis, Beweisart: empirisch, anekdotisch} erstellt werden. Anschließend wird ein erster Plan generiert welcher diese Zielkriterien treffen soll. Zurückgegeben wird ein markdown Formatierter String.

Als eine Kontrollinstanz dient der 'Judge' Agent. Dieser bekommt Input stellt wiederum ein String da. In verschiedenen Stationen des Agenten wird geprüft ob der String den Anforderungen welche Nutzer*innen mitgeben oder der Judge Agent selbst aufgestellt hat entspricht. Anschließend wird auf dieser Basis ein Feedback entwickelt und zurückgeliefert.

Es wird angenommen das alle beteiligten Systeme innerhalb des gleichen Subnetzes in einem Kubernetes Cluster \cite{noauthor_produktionsreife_nodate} und sind mittels Langchain, Langgraph in Python \cite{chase_langchain_2022,noauthor_welcome_2026} und einen FastAPI \cite{ramirez_fastapi_2026} Endpunkt als Gateway realisiert. Es ist bisher nicht beabsichtigt das die Agenten untereinander Kommunizieren. Die Komplette Koordination der Kommunikation liegt bei dem Orchestrator Agent.

Als User-Interface kann OpenWebUI \cite{noauthor_open-webuiopen-webui_2026} als Frontend Layer dienen, um das Multi-Agenten-System \footnote{Wobei hier der Orchestrator als äquivalent zum MAS angeführt werden kann.} anzubinden. Als reines Frontend Layer sind sehr viele Leistungen von OpenWebUI  ungeeignet, jedoch sind viele Möglichkeiten wie die Einbindung von diversen LLM's, RAG Aufbau, Authentifizierungsfunktionen und weitere Methoden für Unternehmen von potenziellen Interesse. Somit könnte eine Beispielhafte Einbindung eines MAS in OpenWebUI als Entscheidungshilfe für diese Open Source Lösung dienen.
